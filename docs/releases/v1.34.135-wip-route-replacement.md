# v1.34.135 — 半成品余量报工与工序替换

## 行为

- 半成品排程按每道工序的实际报工、有效安排和剩余义务计算数量及工时，避免将整批数量重复套用到已部分完成的工序。改排没有工序余量时明确返回原因。
- 报工下拉区分“待处理占用”“已报待核销”和“已报完”；半成品仓展示待处理数量、已排数量和逐工序安排预览，并链接原申报处理页。
- 原待处理申报支持同一半成品批次的多个有效安排合并承接；不足部分可按实际生产日期所在周补排。原申报人员、日期及数量保持不变，单次事务生成一笔正式报工与工时，分配多个来源核销凭据。
- 不足额来源不能伪装成可完成方案。服务端重新校验数量、来源权限及版本，失败保留原申报；完成后沿用原账号通知与工时核销检查。
- 工序行新增“替换工序”，保留原位置，使用新的工序实例，并要求明确新工序标准时间。“保存并预览同步”连接保存草稿和预览，不再要求用户先找另一个按钮；阻断原因直接显示。
- 同步范围支持产品标准和全部未完成工单、产品标准和勾选工单、仅勾选工单。未选工单固定原工艺版本；仅工单变更使用独立冻结版本，产品正式标准保持不变。
- 已报工序退役保留原事实、员工工时和原标准来源。新增检验按真实义务另行报工，不将旧工序记录重命名。预览展示将保留的历史数量；待处理申报或待完成撤回阻止原记录失去可处理的工序，并提供处理入口。
- 新工序可正常报工并闭环；已完成历史工单继续冻结。

## 业务验收

1. 1528 情景：原单 4000，包胶布已报 3300、检验已报 2750；旧安排上的原申报 700 / 1250，在撤排后新安排 700。包胶布恢复 700，检验合并已排 700 与补排 550。原 1250 仅生成一笔报工及一次工时，重复确认幂等，包装剩余仍为 4000，后续仅包装可排 2750。
2. 已开工订单替换未报工工序，再完成新工序和包装，工单完成、成品数量只核销一次。
3. 退役已提前报工的工序保留原员工所得工时，新检验不能获得虚构历史完成。
4. 预览范围与提交范围不一致被拒绝；仅工单变更及未来工单标准均不覆盖未选工单。
5. 待处理原申报不能在工序替换中静默删除或成为孤立记录。
6. 平板 1366×1024 完成替换、保存、范围预览和发布；手机 390×844 使用原二维码实际报新检验，无横向溢出及未捕获脚本错误。

数据库集成使用隔离 PostgreSQL；真实 HTTP 验收使用相同测试订单生成过程，对服务实际发布和报工接口发请求。CI 在固定发布镜像内重复目标业务 HTTP 测试及浏览器交互，再验证国内镜像所有层、匿名拉取、空 PostgreSQL/MinIO 迁移启动、初始密码变更及业务检查。

## 数据与发布边界

本版本无需新增数据库迁移。未对正式订单执行报工、取消申报、修改工艺或切换 Sealos。上线后应在“报工待处理”核对原 700 / 1250 申报是否为真实作业，再确认恢复；测试或误填应通过已有取消/撤回入口处理。已有正式导通报工保留原事实，若选错工序应先做原记录纠错。
