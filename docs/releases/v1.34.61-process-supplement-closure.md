# v1.34.61 补充工序完成后的路线闭环

## 已复现的问题

普通工序允许跨越未完成的补充工序报工。普通工序数量可以已经全额覆盖，但状态仍等待前序补充义务闭环。旧版补充报工只更新补充工序自身，再直接统计普通工序的旧状态，未重新归并顺序组。因此出现“工时/数量 100%，工序仍为当前，路线未完成”。

专项测试在修复前实际失败：普通下游工序期望 `completed`，实际 `current`。这与 GHXS-YPNY-0039 截图相符，但截图不等于对该生产工单完整台账的核查。

## 修复范围

- 补充报工复用普通报工的顺序组状态归并，先刷新普通工序，再判断路线完成。
- 工单完成仍要求成品数量达到目标，且所有有效后代分支已闭环。补充报工不增加成品数量，也不重复回补父工单数量。
- 对已有真实报工对应的按批次待结工时，复用原有幂等结算逻辑；已有工时池不重复创建。
- 日任务同步读取归并后的工序状态。后台恢复以系统审计记录变更，不冒用原报工人。

## 已有卡单的恢复

镜像原有内部后台任务每轮同时检查少量历史卡单，默认每 30 秒一轮，无须重复报工或修改前端显示。

自动恢复仅处理同时满足以下条件的路线：

- 路线仍在生产中，工单未删除、未清理/归档，属于生产计划。
- 存在已履行的补充义务，不存在仍有效的未完成义务。
- 所有未退役普通工序的 `processedQty == inputQty`，仍有有投入量的普通工序错误停留在 `current`。
- 无未覆盖的有效报工；补充工序的独立数量/动作义务已满足，物料数量仍为零。

每条路线在串行化事务中重新验证版本和事实，冲突会整体回滚并在后续轮次重试。恢复只更新状态投影、版本、审计和应结未结的真实批次工时，不创建新的报工或物料流转。仍欠数、补充动作未达标或来源不一致的记录不会被强制完成。

可用 `PROCESS_SUPPLEMENT_COMPLETION_RECOVERY_ENABLED=false` 暂停历史自动恢复；后续补充报工的即时修复不受影响。此变量不是必须新增的部署配置。恢复动作可按 `recover_supplement_route_completion` 查询工艺路线活动和操作审计。

无需新增数据库迁移。使用镜像原有启动入口以保留内部后台任务。发布镜像不代表已切换 Sealos，也不代表生产 0039 的状态已经经过上线核实。

## 验收范围

专项数据库测试覆盖：最后补充工序完成、分批补报、多补充义务、普通工序欠数、活动分支、已计数父工单闭环、成品欠数、延迟批次工时、历史状态恢复、动作义务不足、并发恢复、归档跳过、幂等重放、系统日任务审计。

不可变镜像验收可以在独立 PostgreSQL/MinIO 环境启动后设置 `PROCESS_SUPPLEMENT_RECOVERY_TEST_ORIGIN=http://127.0.0.1:<port>` 和对应测试 worker token，仅运行 `legacy-recovery` 用例。该模式通过镜像中真实的内部 HTTP worker 验证恢复，而不是调用本地恢复函数。
