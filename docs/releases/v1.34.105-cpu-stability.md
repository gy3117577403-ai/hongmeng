# v1.34.105 CPU 稳定性与负载削峰

本版本针对单 Pod 出现 CPU 配额限流、Node 服务连静态健康接口也无法及时响应、后台维护与前台宽查询同时变慢的问题做定向修复。它降低已确认的应用侧放大因素，但镜像发布本身不等于生产已经切换，也不能替代切换后的高峰期观测。

## 已修复

### 图纸关联维护

- `drawing_links` 不再为每一条计划订单完整扫描全部图纸项。
- 图纸项只规范化一次，并按客户、规格、图纸库键、原始字段和 ID 建立索引；订单查找由最坏约 `5000 × 5000` 次比较降为近似线性构建与常数时间查找。
- 保留原有 canonical 选择优先级、歧义时不自动重关联、现有生产工单图纸传播和“已发”状态规则。

### 后台维护稳态保护

- 三个内部维护端点共享同一个进程级 single-flight。上一轮 handler 尚未真正结束时，新请求返回 `409 BACKGROUND_MAINTENANCE_ALREADY_RUNNING` 和 `Retry-After`，不会再启动另一个维护任务。
- 容器后台 worker 严格串行执行五个维护步骤，任一步失败即停止本轮。
- localhost 客户端使用宽松 watchdog 防止 worker 永久无日志挂起；watchdog 只停止等待，不释放服务端 single-flight，因此超时 handler 结束前不会产生重复任务。
- 连续失败按 `30 → 60 → 120 → 240 → 300` 秒有界退避，完整成功后恢复正常间隔。
- 结构化日志记录步骤、状态码、业务错误码、持续时间、连续失败次数和下次等待；进程存活时只报告读取可用性未知，不再误报“reads remain available”。
- 该 single-flight 是进程级保护。当前版本要求后台 worker 只在一个应用实例中启用；如果以后扩为多个 worker 实例，必须先增加 PostgreSQL 租约、leader election 或独立单例 worker，不能把本保护解释为跨 Pod 锁。

### 前台请求削峰

- 生产执行自动刷新从每 30 秒改为约 60–90 秒，并加入每终端随机抖动。
- 继续保持隐藏页面暂停、单请求在途和失败指数退避，降低多台平板整点或同时开机后的同步请求峰值。
- 用户手动操作触发的数据刷新仍保留；远端变化自动出现的时间可能比旧版本晚约 30–60 秒。

### 月计划查询合并

- 月计划容量先读取一次整月快照，再用同一快照计算整月及各裁剪周。
- 当前数据模型下，5 周约 37 次、6 周约 43 次 Prisma 调用降为固定 7 次。
- 保留考勤、日历覆盖、员工任职区间、冻结、半成品来源周、WIP 目标周及缺失工时等原有计算口径。

## 验证边界

- 新增行为测试覆盖三个维护端点共享 single-flight、异常释放、路由 `409`/`Retry-After`、worker watchdog/fail-fast/退避、5000 项索引查找、月/周批量容量与逐范围结果一致以及严格月份边界。
- 完整单元测试、TypeScript、Lint 和生产构建必须通过后才允许创建 `v1.34.105` 标签。
- GitHub 镜像流水线仍需完成 PostgreSQL 集成、迁移、镜像内启动、登录/健康/就绪接口、业务 smoke、不可变摘要和国内代理完整 blob 校验。

## 上线后观察

1. 对比 `drawing_links` 阶段持续时间和 Pod CPU 周期峰值。
2. 观察 cgroup `nr_throttled` 与 `throttled_usec` 增长速度，而不只看平台平均 CPU 百分比。
3. 确认不再出现固定 8 秒的 automatic-finalize 客户端超时，以及 `BACKGROUND_MAINTENANCE_ALREADY_RUNNING` 不持续累积。
4. 记录 `/api/health`、`/api/ready`、`/api/auth/login` 和 `/api/work-orders/execution` 的 P95/P99、5xx、连接池占用与 PostgreSQL 等待事件。
5. 如果生产执行数据规模继续增长，下一阶段应把当前全周摘要/安排读取后的内存分页改为数据库分页与聚合；本补丁没有冒险改变该业务结果。

## 回退边界

- 本版本不新增 Prisma migration，不改写业务数据。
- 镜像发布不等于 Sealos 生产切换。切换前应记录现网不可变 digest 并备份 PostgreSQL；回退时使用已验收且与当前数据库结构兼容的 digest。
