# v1.34.77 首页消息生命周期与视觉收敛

## 用户问题

- 首页实现与已选“智能工厂指挥舱”样板存在明显视觉偏差。
- 已经处理完成的工艺事项仍长期计入“待处理”。
- 只有“已读”，没有“已完成”，无法整理个人消息收件箱。
- 本地预览服务中断时直接显示英文 `Failed to fetch`。

## 根因

`v1.34.76` 把工艺提交、审核、驳回、启用和补充报工等不同阶段都保存成独立 `APPROVAL` 通知；待处理统计既不检查个人完成状态，也不在后续阶段到达时收口旧阶段。因而历史事件留痕被错误地投影成当前待办。“已读”只表示看过，不能代表业务或个人待办已经完成。

## 修复内容

- `SystemNotificationRecipient` 增加 `completedAt`、`completionKind`、`completionReason`。
- 通知 API 支持 `state=pending|completed`，并返回服务器全量统计。
- 单条消息支持手动完成；仅手动完成允许恢复。
- 业务后续阶段自动归档旧阶段，自动归档记录不可误恢复。
- 工艺驳回、启用完成、补充义务完成和补充报工进度直接进入历史，不再累计为审批待办。
- `FAILED` 等未解决状态采用保守策略，不因历史清理而隐藏。
- “已读”“稍后提醒”“个人完成”“底层业务解决”保持独立语义。
- 首页增加醒目的“待处理 / 已完成”切换，并显示完成时间与原因。
- 完整消息中心同步增加“待处理 / 已完成”、业务分类、搜索、游标分页、人工完成与安全恢复；超过 100 条后仍可继续加载和检索。
- 网络中断显示中文可重试提示，不再把浏览器原始错误直接呈现给用户。
- 首页结构、比例、底纹、节点层级和消息密度重新向选定样板收敛。

## 数据边界

- 迁移只归档可以由事件顺序或明确终态证明已经结束的历史工艺提醒。
- 不删除 `SystemNotification` 事件历史。
- 不伪造审批、启用、报工或工时记录。
- 手动完成只整理当前用户的个人消息，不改变底层业务状态。
- 自动源状态对账当前覆盖工艺路线变更通知；其他来源仍可人工完成，后续应在各业务终态事件中逐类接入自动收口。
- 本版本仅发布镜像，不自动切换 Sealos 或正式数据库。
