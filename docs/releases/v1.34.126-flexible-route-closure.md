# v1.34.126 工序自由调整与报工核销

本版修复工艺调整后“全部工序显示完成，但工单无法结单”的数量与状态脱节。

- 已发生报工的批次在发布工艺调整时保存原数量流转顺序，页面使用新工序顺序。部分报工、并行工序、连续调序、删除和补充工序不会把同一批材料再次投入或重复计为成品。未开工批次使用新工艺顺序。
- 新增工序继续要求整批真实补充报工。允许相邻工序存在不同的部分进度；不把这些进度当作自动完成新增工序的证据。
- 普通工序存在待核销报工时不能自动标记为已跳过。已完成的普通工序与未完成的补充义务分别显示，流程中心明确区分已完成、已跳过、报工待核销。
- 已移除工序的报工保留历史，其待核销状态不再阻塞现行路线。删除工序的效率冲销沿用原有带审计的规则；本版核销恢复本身不重复计算已记工时。
- 对历史零投入、零材料产出工序，后台只有在查到整批有效跨越流转，或数量一致的整批成品台账时才转成独立实际报工义务。既有报工按原记录核销；没有真实报工的检验继续待报。恢复保留原报工编号、时间、参与者和已记工时；此前延后的按批工时在条件满足时记入一次。
- 历史恢复跳过暂停、动作数量、返工/分支及不良场景。每轮最多 3 条候选，使用事务、版本和唯一约束保证重试安全，并保留恢复活动、覆盖依据和操作日志。
- 完工撤回按工序身份查找原数量流转，避免调序或插入造成序号变化后回退错误的材料；独立补充报工撤回不扣减已经形成的成品。

## 数据库升级

新增可空的 `work_order_process_steps.material_sequence_group`，以及带唯一约束和来源校验的 `process_supplement_obligations.reconciliation_key`。启动时运行 Prisma migration；迁移不批量改写正式报工或产量。历史恢复由应用原有维护任务在运行后按证据逐批处理，可使用 `PROCESS_PENDING_COVERAGE_RECOVERY_ENABLED=false` 关闭。

## 验证

新增 7 个 PostgreSQL 场景：部分报工后连续调序及插入、调序后撤回重报、并行变更、删除待核销工序、整批已报历史恢复、缺少检验的恢复与补报、首工序历史缺口与按批工时。发布验收对待交付的真实镜像再次通过 HTTP 登录、预览/发布工艺、普通与补充报工、撤回、恢复任务完成这些场景。

同时运行现有报工、补充义务、删除工序、撤回、数量覆盖、权限、质量与计划导入回归。国内镜像验证包括摘要、平台、所有层完整性、匿名完整拉取及独立 PostgreSQL/MinIO 环境启动。

镜像发布不等于 Sealos 应用切换。正式工单是否已恢复，应在切换后按恢复日志和实际补报结果确认；缺少检验记录不会被自动补成完成。
