# 按批工时分日入账与旧账核对

v1.34.145 对普通按批工序采用 `batch_proportional_v1`。整批预算为已确定的整批标准工时加准备工时；本版本两部分一起按有效良品数量占冻结目标数量的比例分摊，不推测实际调机人员。每次报工保留原生产日期与参与人，多人共享本笔工时，最后补足批次数量的一笔承接整数毫秒尾差。前序补齐只核销物料，不再增加该笔劳动。

本笔撤回释放本笔数量与工时，不回退其他人的已完成劳动。只要仍有有效贡献，后续报工继续使用冻结目标和预算；全部贡献撤回后，新报工采用新的有效标准。整批标准变更会统一按贡献重算；单笔主管标准更正不允许将一份工时改成完整批工时。

数量明确而标准缺失时，保留原完成记录、原员工、原日期及 `LOCKED` 工时池，并生成可在原业务界面查看的待完善回执；此时没有可量化工时，不伪造数值。有效标准发布后，既有恢复 worker 可自动续接同口径、无来源歧义的报工，系统审计与人工核定分别记录。数量换算、半成品来源/周次以及已有不同标准必须先核对业务依据。

## 历史数据

迁移只增加字段和约束，不批量改正式历史工时。有完成记录但尚无工时池、且标准和目标明确的按批工序，可在下次该路线报工时逐笔补建，或使用以下工具预览。旧版已有效结算的整批池保持原账，工具返回 `blocked` 原因，不把新比例池叠加到旧完整预算上。已撤回的旧池不会阻断新的报工。

在已配置正确数据库连接的受控工作目录中执行：

```powershell
npx tsx scripts/reconcile-batch-labor.ts --route=<工艺路线ID>
```

默认仅输出 JSON 预览，包含 completionId、stepId、原生产日期、原参与员工、数量、预计毫秒数和不能自动处理的原因。核对目标路线、原数量、日期、员工和整批总额后，使用：

```powershell
npx tsx scripts/reconcile-batch-labor.ts --route=<工艺路线ID> --execute
```

执行使用串行化事务；重复执行不重建已有池。没有池且没有有效标准的记录只能保留待核定状态。已有旧版有效整批池或冻结目标冲突的记录需要单独核对，不能用本工具强制覆盖历史。

## 验证

`tests/batch-labor-proportional-integration.test.ts` 覆盖跨日多人、前序未补齐即时分配、幂等重放、补前序不重记、撤回前序保留下游、撤回本笔后重报、旧无池数据预览/修复/重复执行、旧有效池保留、撤回旧池后重报及全部撤回后使用新标准。`tests/process-report-submissions-integration.test.ts` 覆盖缺标准回执与已发布标准自动续接，包含当前工序标准先更新而恢复 worker 尚未运行的情况。
